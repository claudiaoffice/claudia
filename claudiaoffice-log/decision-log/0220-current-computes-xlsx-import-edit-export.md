# D220 · `claudia-computes-io` gets the same real import/edit/export path D217 gave docx and D219 gave pptx, now for xlsx: `xlsx_to_workbook` (a worksheet's cells…

**`claudia-computes-io` gets the same real import/edit/export path D217 gave docx and D219 gave pptx, now for xlsx: `xlsx_to_workbook` (a worksheet's cells become a `Sheet`'s typed contents, a formula kept as its text and recalculated by the model's own calculator after import) and `apply_edits_to_xlsx` (re-export by patching only the cells that actually changed on each touched sheet, via openpyxl's live object API, then `reconcile`-ing against the original bytes).** The parts `reconcile` is told claudia owns are exactly the touched sheets' own worksheet XML parts, resolved through `xl/workbook.xml` and its rels by the existing `_sheet_part` helper (built for `add_pivot_table`, D147) — never `xl/styles.xml` or `xl/sharedStrings.xml`, which `claudia-opc-io`'s own docstring had flagged as needing a real per-entry merge the whole-part reconcile strategy cannot give them. That merge turned out to be unnecessary rather than deferred: confirmed empirically (seven probes against openpyxl directly, mirroring D217/D219's own pre-code validation habit) that openpyxl abandons the shared-string table on every save of its own accord (every string becomes an inline string, regardless of how the source file encoded it), so a touched sheet never needs the shared table and an untouched one keeps referencing the pristine, reconciled-back original; and that openpyxl preserves a workbook's exact style-index numbering through a round trip as long as no style, font or fill is touched, which this module never does (cells carry no per-cell style in claudia's model). A separate probe found that openpyxl mutates an embedded picture's drawing XML on **any** load-and-resave, even with zero related edits — a pure round-trip artifact, not caused by an edit at all — which is exactly why owning only the touched sheets (never the whole package) matters: a picture or chart on an untouched sheet is reconciled back to its pristine original regardless of what openpyxl's own resave did to its copy of it. `apply_edits_to_xlsx` raises `UnsupportedEdit` for adding, removing, renaming or reordering a sheet; changing or clearing a cell's content, including adding a brand-new one, is supported, since that is just another cell's content changing to or from `None`. The test-document library (D218) gets its third format: `claudia_test_documents.adapters.ADAPTERS["xlsx"]`, three xlsx fixtures (cells and a recalculating formula; a chart and a picture, each "beyond claudia" — openpyxl's own object model gives `xlsx_to_workbook` nothing to see there either — both part-level, since a chart's definition is never inline in any worksheet's own XML the way a pptx table is), generated by the same `_build_fixtures.py`. 16 computes-io tests (9 new, 7 pre-existing `workbook_to_xlsx`/`add_pivot_table` ones unchanged), no regression; all 10 catalogue entries (4 docx, 3 pptx, 3 xlsx) pass the gate.

**Notes.** Follows D217's and D219's design exactly, with xlsx's own structure landing between the two: like pptx (and unlike docx's single `word/document.xml`), xlsx keeps each sheet in its own part, so the owned-parts set can be the actual touched sheets rather than one fixed, coarse-grained part; like docx, cells on an untouched sheet needed no reasoning about relationship-id stability (xlsx's sheet-part-by-rels resolution, `_sheet_part`, already existed from the pivot-table spike and needed no change). The one genuinely new risk — the shared-string/styles whole-part reconcile gap `claudia-opc-io` had flagged in advance — was closed by seven probes against real openpyxl output *before* writing `xlsx_to_workbook`/`apply_edits_to_xlsx` at all, the same "validate against the real library first" discipline D147's three spikes and D217's own design discussion both used, rather than building the per-entry merge the docstring's own wording might have suggested was required.
