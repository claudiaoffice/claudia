# Claudia — Decision Log
 
Format: `ID · Decision · Date · Notes`. A decision is replaced, never deleted: the old entry is marked *superseded by Dxx*. "Proposal" in a note means it is Claude's suggestion, not yet agreed.
 
## Vision
 
> Claudia is a privacy-first office suite of three quiet, elegant apps (composes, computes and creates) that you can run on your own hardware. Documents live on a server you choose, are shared live with colleagues, and an AI that runs where you decide works in the document as one more participant, bound by the same rules as everyone else. The interface stays out of the way and keeps its power in menus and context. The goal is to help people think with their data and ideas, not only record them.
 
Design character: a hint of female elegance, technical precision, technical power. Inspiration: Bret Victor (co-thinking, understanding through interaction, visualization and simulation).
 
A proposed addition about stories across the three apps is in `product-vision.md`; it is not part of the statement until the owner agrees.

## Security, calculation and extensibility (second round)
 
| ID | Decision | Date | Notes |
|---|---|---|---|
| D34 | Encryption defends against **outsiders holding the file** and against **co-editors** who must not see parts of the history or chat. | 2026-11-01 | Design: key slots per password; keys per domain (content, history, chat); commands grouped in blocks that are compressed, then encrypted; redaction rewrites a block. Per-command or per-recipient keys only if private messages must be unreadable to a third password holder (needs public keys): not in version 1. The server sees plaintext only while someone has the document open. A lost password means a lost document unless a recovery key is offered. |
| D35 | **Users live inside the document**: each has a name, their own password and a role. | 2026-11-01 | The history shows authenticated names. `ai` stays a protected name. |
| D36 | **Calculation happens on the server** (most if not all). Clients display values and keep no calculating replica. | 2026-11-01 | Clients no longer need plugin files, nor pandas/numpy in a client-only install. Cost: every edit needs a round trip; slider drags on a remote server must coalesce requests (latest wins). Supersedes the demo's replica-calculating GTK client. |
| D37 | **Performance architecture:** incremental recalculation with a persistent dependency graph. The output range of a function is owned by it (like SQL results). Inputs are not locked: a worker computes on a copy of the inputs at revision r and its result is discarded if the inputs changed meanwhile. Results of worker functions are stored in the log as commands with final values (large ones as content-addressed blobs), tagged with the function version. Two tiers: core and quick vectorised functions inline, heavy or slow functions in warm worker processes with timeouts. The kernel stays free of I/O, so a document can later run in its own process. Dragging a value uses an unlogged "what-if" preview. Cells get a "calculating" state. | 2026-11-01 | Python 3.14 uses forkserver/spawn: functions and arguments must be importable and picklable. SQL cells use the same worker path. |
| D38 | **UserFunctions are installed by the server admin** in version 1, from a folder on the server, and run in workers. A document declares what it requires (name, version, digest), like fonts. On a localhost setup adding a function must be really simple. | 2026-11-01 | Proposal for localhost: the folder sits in the user's profile; Tools ▸ New Function… creates a file from a template; saving reloads the workers, and a new digest marks results of the old version stale. Same trust rule everywhere: whoever controls the server's folder controls the functions. No executable code travels inside documents. |

## Kernel and server (sixth round)
 
Details: `core-kernel-notes.md`. D45–D49 were decided in the Epic 1 discussion; D50 is a proposal made while building E3.1.
 
| ID | Decision | Date | Notes |
|---|---|---|---|
| D45 | **Revision identifiers are `(branch, seq)` with a parent link**, not content hashes and not bare integers. | 2026-11-02 | Sequence numbers continue along a branch from its fork point; redaction never changes an id; no tamper evidence from the id itself (the container can add a hash chain later, E2.5). |
| D46 | **Undo is per author and never overwrites a colleague.** If a colleague wrote the same cell (region) after my step, my undo is refused (`UndoConflict`) and nothing is consumed. | 2026-11-02 | Implemented by `Command.shifted_by`: the stored inverse is moved through everything that ran since; `None` means "changed by somebody else". The demo executed the stored inverse as it was, which hits the wrong element when two authors insert at indexes. |
| D47 | **`execute` enforces locks for everybody, the `ai` user included.** A command that touches a region a colleague holds is refused (`RegionHeld`, protocol code `locked`) and changes nothing. | 2026-11-02 | Undo checks the same rule. Replicas replaying accepted entries are not checked. `check_free` stays public so a UI can ask in advance. |
| D48 | **Restoring a checkpoint forks.** The document continues on a new line `restore-N`; the old future stays in the log under its unchanged revision ids on a hidden side line until an owner discards it. **`switch_to` is the way back** to any line (also recorded in the log). Nothing is ever truncated by a restore. | 2026-11-02 | Everybody's undo steps, checkpoints and model are those of the line they are on; locks and presence are cleared; views get `BranchSwitched` and `Rebuilt`. Discarding side history is the owner's act (permission check: E2.3). Rules for a live multi-user session: D51 and D52. |
| D49 | **An edit made against a view that is no longer on the active line is refused** with `StaleEdit` (protocol code `stale`) and changes nothing. | 2026-11-02 | Edits in flight while somebody restores or switches must not land on a document the author is no longer looking at. `Document.execute(command, base=revision)`; the server's `apply` takes `base`. Clients reload (`snapshot`) and try again. |
| D50 | *Proposal; the part about listing is **superseded by D53**, the rest is not yet confirmed.* **Server access:** credentials travel in the first WebSocket frame (`hello`), never in the URL; name plus password per document (D35); the first person who asks for a document that does not exist becomes its owner; a wrong password, an unknown name and a missing document give the same answer; the name `ai` is refused; ~~there is no endpoint that lists documents~~ (reversed by D53); TLS by default with a self-made certificate whose fingerprint the client trusts like an SSH host; a browser page from another origin is refused unless named. | 2026-11-02 | Carried over from the demo (TLS, fingerprint trust, redirect port) and adapted to D20 and D35. With D53 "a missing document and a wrong password give the same answer" can only hold for documents that are not listed. |
 
## Live sessions (seventh round)
 
| ID | Decision | Date | Notes |
|---|---|---|---|
| D51 | **Restoring a checkpoint in a live session needs the consent of everybody who is editing.** Any editing user may propose going back to checkpoint X. All other users currently editing get a banner that informs them and asks for their consent. Only if all of them agree is the checkpoint restored; the old history then stays on the hidden side line (D48). A user who contributed, logged out and is not present during the consent phase is not asked. A **later feature** will let users see the lines and select one to go back to. | 2026-11-02 | Refines D48. The kernel already restores, lists lines and switches (E1.7); the consent flow and the wire methods are E3.7, the line picker is E3.8. Details: D52. |
| D52 | **Details of the consent flow (D51).** (1) *Who is asked:* connected users with the role owner or editor. Viewers are told but never asked and never block. The `ai` user is never asked and never blocks; its running jobs are cancelled or marked stale when the restore happens. If the proposer is the only one editing, the restore happens at once. (2) *How a vote ends:* any "no" ends it at once; one open proposal per document; the proposer can withdraw it; a proposal that is not answered by everybody expires after a fixed time (two minutes to start with) and nothing changes. The banner shows who has agreed and who has not. (3) *People coming and going:* someone who disconnects during the vote is no longer asked; an editor who connects during the vote is added and asked. (4) *Work during the vote:* editing continues normally; when the restore happens, edits in flight are refused with `stale` (D49), and the banner afterwards says what happened and offers to copy what was refused; locks and presence are cleared (D48). (5) *Switching back to a hidden line* (`switch_to`) follows the same consent flow. (6) *Users who were away:* on return they get a notice: restored by A to checkpoint X with the agreement of B and C; your N commands are on a hidden line. Until the line picker exists (E3.8) that work is not reachable for them; discarding side history stays the owner's act. | 2026-11-02 | The six proposals made with D51 were accepted as they stood. The expiry time of two minutes was an example in the proposal and is a starting value, to be tuned with real use. Implementation: E3.7. |

## Open design questions
 
- Typesetting service: which renderers (spike with sample formulas and help pages), bundle size, TeX security settings. *Widened by D88:* a full engine (Tectonic is the first candidate; to verify offline, with biblatex and Beamer), a curated and pinned package set, a sandbox (no shell escape, no files outside the job, no network, limits), and whether the live preview of a formula needs a faster engine than the final output.
- **Bibliography and LaTeX (D86–D88). Claude's proposals, none decided:**
  1. *"In the core" (D88):* a shared service package (`claudia-typeset`) used by the three servers, not the kernel; the kernel stays standard library only.
  2. *BibTeX details (D86):* BibTeX entry types and fields as the base, biblatex extras accepted and kept, nothing dropped on a round trip; the entry keeps its original text for export and shows decoded text (accents) in the interface; citation keys unique per document.
  3. *Connectors (D86):* an extension point with the help contract (E13.2); runs in the client or shell when it needs the local application, with credentials sent from the client per request and never stored in the document; entries copied into the document carry provenance (library, item key, version) and are updated only after asking, as in D72. The spike E9.18 finds out what Zotero and Mendeley really offer.
  4. *Citation styles:* CSL (used by the reference managers) or BibTeX/biblatex styles through the LaTeX engine; the same style must give the same list in the browser and in the export.
  5. *Page view (D61, D88):* with the full engine the page view could be typeset by it (server-side layout), so page view and PDF match; cost is latency and a second layout engine beside the flow view.
  6. *LaTeX import (D87):* a defined subset plus raw LaTeX blocks for the rest.
  7. *Beamer export (D87):* shapes map to TikZ paths directly (the format of D78); the template maps to a Beamer theme (generated or standard, open).
- **Help system (D76). Claude's proposals, none decided:** (a) topics are files with structured metadata and a body in the LaTeX subset of D30, with at least one worked example, linked to what they explain (action ids, function names); (b) a server help service with full-text search (SQLite FTS5) that works offline for every role; (c) an extension without tooltip and help is refused at load (computes now; composes and creates once their macro API exists, D29), and its examples are run as tests; (d) help shows in a tab of the docked right panel, never an overlay; (e) help text from extensions is untrusted data for the AI; (f) every menu action and dialog must have a topic, checked in CI; (g) live "try it" examples later (E13.7). - **Styling in CSS (D73): the six points are decided as D75. Still open:**
  1. *Deleting a style that other styles are based on.* *Proposal:* deleting never changes how anything looks and never leaves a dangling reference. If styles are based on it, the person chooses: **keep their look** (default: each child takes over the properties it inherited and is re-based on the deleted style's parent) or **re-base them on another style** (appearance may change; a preview is shown). If content uses the style, a replacement must be chosen first, with a preview. Root, built-in and template styles cannot be deleted, only hidden. Deleting is one command and one undo. If a colleague applies the style at the same moment, their command is refused ("this style was deleted") and their client refreshes. Alternative to consider: refuse deletion while children exist, which is simpler but forces the person to re-base by hand. Story: E1.10.
  2. *The first allow-list of CSS properties* (proposal in E1.10).
  3. *Row heights and column widths:* style or sheet layout? *Proposal:* layout (E6.13).
  4. *Where the dialog appears* (side panel, popover or modal): a mock-up decides (E5.13).
- **The document list (D53), details. Proposals, not decided** (the demo already lists `id`, `app`, `modified` and `online`, openly, D57):
  1. *Who may see the list.* The server has no accounts (D20), so there is nobody to log in as. *Proposal:* an optional server access secret set by the administrator; if set, listing and creating documents require it. On a localhost install there is none and the server accepts only connections from the same machine.
  2. *What the list shows.* Document id, a title chosen by the owner, app type, last change and size. Never content, user names or history. The title must be readable while the document is sealed, so it is stored outside the encrypted parts of the container (E2.1): anyone holding the file can read it. The owner chooses the title knowing this.
  3. *Unlisted documents.* The owner can mark a document as unlisted: it does not show in the list and is opened by id. For an unlisted document the answer to "missing" and "wrong password" stays the same (D50); for a listed one it cannot be hidden that it exists.
  4. *Who may create documents.* With a server access secret, only those who know it; the first person who asks for a new document becomes its owner (D50). Without one, only local connections.
- **Stories across the suite (D58–D69). Claude's proposals, none decided:**
  1. *(Confirmed as D72; updates only after asking.)* *How material moves between apps (D65).* A server cannot open another app's document from disk: it is encrypted with that document's passwords and the server holds keys only while the document is open. *Proposal:* the person's client opens both documents (name and password for each) and an action such as "insert from computes" pulls a rendered result (chart image and data) into the composes document as an embedded item with **provenance**: document id, server, range or chart name, revision. When the source has changed, composes says "the source changed since revision X, update?" as an explicit pull, which also shows what changed. No server-to-server trust and no shared keys. Translation work ("write up what this model shows") is done by the AI server with a session in each document, under the asker's rights (E7.4). Documents on disk stay the unit of exchange.
  2. *(Replaced by D71: optional metadata derived from "What would you like to achieve with this document?"; no mandatory brief.)* *Where goal and plan live (D59).* *Original proposal:* a **brief** per document: goal, audience, purpose, current phase, and the plan as an outline, stored in the document as commands and shown beside the work (for example in the docked panel). The plan's items link to the work they concern (a paragraph, a slide, a range), so the AI and the person can see drift in both directions: work that is not in the plan, plan items without work. When the AI derives a presentation from a text, the new document gets its own brief and a provenance link to the source. No fourth app and no central project object.
  3. *(Folded into D71.)* *Phases (D60).* *Original proposal:* the phase is a logged command; the AI may suggest a change with a reason; the person accepts or dismisses; a dismissal is remembered for that document, so it does not nag.
  4. *Claims and evidence (critical thinking, D58).* *Proposal:* where a text statement cites a number or chart, the author can link it to its source (the provenance of point 1). The AI can then check that text and data agree ("the text says 12 %, the sheet says 9.8 %") and can play a sceptical reader asking what the audience would ask. This is a tool the author may use, not a rule.
  5. *Suggestions and authorship (D63).* *Proposal:* an AI suggestion is a proposal object anchored to a text Region (D17), not a change to the document; accepting it makes a command attributed to the person who accepted it, with the suggestion's author recorded; suggestions are not blocked by the ± n words zone (D11); a suggestion is marked outdated when its anchored text has changed. The **authorship view** (text coloured by author, or by time) is derived by replaying the log (D15) and needs no extra storage, but the text commands must keep the identity of runs that are moved or pasted. Whether human reviewers also get a suggest mode is open (blocked-decisions table of the backlog).
  6. *Naming styles (D62).* *Proposal:* the invitation to name a style never blocks typing; unnamed styles collect in a "to name" list. Importing a Word file that is full of direct formatting: the AI proposes named styles from repeated formatting, and the person confirms.
  7. *Mermaid and LaTeX (D66).* *Proposal:* both are rendered in the frontend. The source text is the truth and the rendered SVG is a cache stored in the document (like snapshots, D15), so exports to docx, odt, pptx and odp can use the stored SVG without a browser on the server. Rendered output from outside is shown as an image, never inline, and sanitised on export.
  8. *Slide templates (D68).* *Proposal:* a slide is **content in typed slots** (title, bullets, figure, quote, formula, diagram) plus a **layout** from the template. The slide always shows which template and layout it comes from. Page number, footer and title style belong to the template and cannot be formatted on the slide. A deviation is allowed only as a **named variant** (the rule of D62). Changing the layout re-flows the slots; it never moves free-floating objects. Free-form shapes exist but are few and deliberately limited (D67).
  9. *(Decided as D70.)* *Order of file formats (D5, D67, D69).* ODF (odt, ods, odp) first in all three apps, Microsoft's formats second. Whether public administrations require ODF is still to verify per country.
  10. *Public organisations and schools (D69).* Things this implies, to turn into stories later: accessibility, plain-language checks as an AI thinking aid, official templates (for example a German business-letter layout), self-hosting by the organisation, and no data leaving the server unless the administrator opts in (D32).
