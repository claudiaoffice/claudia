# D219 · `claudia-creates-io` gets the same real import/edit/export path D217 gave docx, now for pptx: `pptx_to_slides` (a text box or one of the three built-in…

**`claudia-creates-io` gets the same real import/edit/export path D217 gave docx, now for pptx: `pptx_to_slides` (a text box or one of the three built-in autoshapes becomes a `SlideObject`, position and size read back through the presentation's own slide size rather than a fixed 16:9 assumption) and `apply_edits_to_pptx` (re-export by patching only the slides whose objects actually changed, then `reconcile`-ing against the original bytes).** Unlike docx's one `word/document.xml`, pptx keeps each slide in its own part, so the parts `reconcile` is told claudia owns are computed fresh per call from exactly the slides an edit reaches — every other slide, layout, master, theme and media part comes back byte-for-byte, not merely semantically unchanged. A picture is not imported as claudia's own "image" object kind: `slides_to_pptx` cannot write one yet either, so there is nothing symmetrical to export it back out as — it stays beyond-claudia content, same as a table or a chart. `apply_edits_to_pptx` raises `UnsupportedEdit` for adding, removing or reordering a slide or an object, for reordering the objects on a slide (stacking order is not one object's own field, so a per-object diff cannot see it), and for changing an object's kind or shape outline. The test-document library (D218) gets its second format: `claudia_test_documents.adapters.ADAPTERS["pptx"]`, three pptx fixtures (a text-box-and-autoshapes case; a table and a picture, each "beyond claudia," mirroring docx's own table/image split between element-level and part-level preservation), generated by the same `_build_fixtures.py`. 11 new creates-io tests (29 in that package overall), no regression in the 7 pre-existing ones; all 7 catalogue entries (4 docx, 3 pptx) pass the gate.

**Notes.** Follows D217's design exactly where pptx's own structure lets it do even better: a per-part OPC package (one XML part per slide, versus docx's single large part) means the owned-parts set for `reconcile` can be the *actual* touched slides rather than one fixed, coarse-grained part, confirmed empirically (editing one slide's text and saving leaves every other slide, layout, master, theme and media part byte-identical even without reconcile's help — reconcile is kept anyway as the same defensive restore-everything-not-owned stance D217 took, not relied on as the only guarantee). No `export_checks`-style fixture (docx's tracked-change-suggestion analogue) is included: `add_transition` (D147) is pptx's one feature claudia can write but not reimport, but it is a standalone function outside `apply_edits_to_pptx`'s own flow, with no natural hook in the `Adapter(import_fn, apply_edits_fn)` contract to exercise it through the catalogue without extending that contract — left out rather than forced in.
