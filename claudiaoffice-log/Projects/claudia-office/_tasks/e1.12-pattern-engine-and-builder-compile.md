As an app developer, I want one place that turns a builder description into a pattern and finds matches with it, so that all three apps, both clients and the AI mean the same thing by a search.

**Acceptance:** `claudia_core` has a `Search` model (parts, conditions, options) that compiles to a find pattern, a cell filter pattern and a replacement template; a `find` over any sequence of `(location, text)` returns spans and kept parts; a typed pattern is validated with the position of the first mistake; evaluation stops at a time budget and says so; the sentence restating a search is produced from the model with whole translatable strings; every builder phrase in the vocabulary of `notes/search-and-replace.md` has a test that states the pattern it compiles to; no sorting, ordering or location knowledge of any app is in it.

**Notes:** Written test first (TDD): the compile table of the note becomes the first test file. Python `re` only (D284); if `\p{L}` or timeouts turn out to be needed the `regex` package is a one-line swap behind the module. Catastrophic backtracking is the risk: tested with `(a+)+$` on a long text.

**Status evidence:** 2026-11-13: built test first. `packages/claudia-core/src/claudia_core/search.py` (core 0.17.0) with `tests/test_search.py` (about 110 tests: every builder phrase states the pattern it compiles to; `(a+)+$` and other hidden backtracking shapes are refused before they run; error positions; size caps; the time budget; `RecursionError` is caught). Python `re` only (D284). One change from the acceptance text: the **sentence restating a search** is produced in the web client (`web/app/lib/search.ts`, `sentence()`, tested in `web/tests/search.test.ts`), because its whole translatable strings live in the web catalogue (`po/de.po`); the core produces the patterns, never prose. Notes: `implementation-notes/search-and-replace.md`.
