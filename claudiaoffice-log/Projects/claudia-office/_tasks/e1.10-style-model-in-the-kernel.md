As an app developer, I want one style model (named styles whose properties are CSS, with inheritance and commands) in the kernel.

**Acceptance:** a style has id, name, kind, optional parent and a set of CSS properties, storing only its differences, with no cycles; **only an allow-list of CSS properties and value types is accepted** — no `url()`, `@import`, `@font-face`, external references, scripts or outside `var()` — refused when the command applies, naming the offending property, and versioned like command schemas; commands create, rename, change, deviate, delete and apply, all logged and undoable per author; names unique inside a document; changing a parent changes every child that has not overridden; **deleting a style never leaves a dangling reference**, with the person choosing "assign another style" (the default, the plain style of the kind preselected; says how many looks change, D785) or "re-base on another style" (which keeps every look), and root, built-in and template styles only hideable.

**Status evidence:** built as `claudia_core.css` (`CSS_VERSION` 2, `validate_css`, `parse_css` with line-numbered problems, `format_css`, `resolve_css`) and `claudia_core.styles` (`StyleDef`, `StyleBook` with `based_on` inheritance, `CreateStyle`, `ChangeStyle`, `RenameStyle`, `RemoveStyle`, `StylesChanged`), with two-author conflict tests. An object's own style can now be repointed (`core.SetObjectStyle`), and the methods a document needs are shared by all three apps (`claudia_server.styles`, D203). Colour is a second axis beside the styles: `claudia_core.palette` holds the document's nine **colour roles**, a style writes `@accent` or `@accent/55`, and a client draws from the `resolved` form so that what reaches a browser stays literal (D200–D202). Every built-in style in all three apps is written in roles, so no literal colour is left anywhere in a new document. All three apps now have the style menu itself, not only the model behind it (D209): one `StyleMenu`/`StyleSpec`/`StylesDialog` reached through a `StyleHost`, with `objectStyleHost` making the selected floating object the thing a menu styles in creates and computes, `deviate_object_style` for "change this shape only", and a Format menu in each app in place of the inert "No styles yet" stub. Colour is picked by meaning: the picker lists roles by name and purpose, a literal colour reads as a deviation that one click adopts away, and the Colours dialog says what a change will cost before it is made, in plain words and never as a ratio (D210). **Not done:** `kind` on a style (now decided, D305, and built as E1.11) — composes' Format menu leaves the object styles out *by id* for want of it; the full delete rules (`RemoveStyle` exists only as the undo of a create); upcasting of dropped properties; the style kinds for cells (E6.13); and a command that lets a person define a role of her own (`ReplacePalette` can bring a different set, which is what "the colours it started with" uses; nothing adds one).

**Checked against the code, 2026-11-17 (`main` at `6814bac`).** `CSS_VERSION` is 4 now (`hyphens`, E9.25). Deleting a style by the rules above is still not built: `RemoveStyle` is only the undo of `CreateStyle` and is refused while anything uses the style (D226 is still open).

**Deleting and hiding, 2026-11-17 (branch `style-delete`).** The kernel, the three apps' models and the server are built: `plan_delete_style` in `packages/claudia-core/src/claudia_core/styles.py` deletes a style as one undoable step that holds every look (*assign another style* or *re-base on*; D785), with a stand-in style `<name> (kept)` for what had the style itself; `RebaseStyle` and `SetStyleHidden` are commands; `StyleDef` has `origin` and `hidden` (D780); the server has `style_deletion`, `delete_style` and `hide_style` in `packages/claudia-server/src/claudia_server/styles.py`. The rules are D226 and D780–D782; notes in `claudiaoffice-log/implementation-notes/implementation-notes-style-deletion.md`. **Not done:** a command that lets a person define a role of her own (to be its own story). Upcasting of dropped properties is dropped: not wanted before the first release (D308). **2026-11-18:** two ways, *assign another style* (`how="assign"`, the default; the one way that changes looks) and *re-base on another style* (D785, superseding D784).

**Screens, 2026-11-18 (branch `style-delete`).** The mock was approved and the web client is built (D783, D786): *Delete…*, *Hide*/*Show* and *Show hidden styles* in All styles, the confirmation with the two ways, the announcement with *Name it…* and *Undo*, hidden styles out of the menus, German strings, Alt access keys; browser check `npm run e2e:style-delete`. The desktop shells open the page's dialog (D301) and needed no new entries. **Open:** whether re-basing should apply only to styles based on the deleted one; and what to do when the look needs font, size, colour or alignment (no neutral value to hold it, D781).
