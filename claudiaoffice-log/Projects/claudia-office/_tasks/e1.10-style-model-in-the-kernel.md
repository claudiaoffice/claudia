As an app developer, I want one style model (named styles whose properties are CSS, with inheritance and commands) in the kernel.

**Acceptance:** a style has id, name, kind, optional parent and a set of CSS properties, storing only its differences, with no cycles; **only an allow-list of CSS properties and value types is accepted** — no `url()`, `@import`, `@font-face`, external references, scripts or outside `var()` — refused when the command applies, naming the offending property, and versioned like command schemas; commands create, rename, change, deviate, delete and apply, all logged and undoable per author; names unique inside a document; changing a parent changes every child that has not overridden; **deleting a style never changes how anything looks and never leaves a dangling reference**, with the person choosing "keep their look" or "re-base on another style", and root, built-in and template styles only hideable.

**Status evidence:** built as `claudia_core.css` (`CSS_VERSION` 2, `validate_css`, `parse_css` with line-numbered problems, `format_css`, `resolve_css`) and `claudia_core.styles` (`StyleDef`, `StyleBook` with `based_on` inheritance, `CreateStyle`, `ChangeStyle`, `RenameStyle`, `RemoveStyle`, `StylesChanged`), with two-author conflict tests. An object's own style can now be repointed (`core.SetObjectStyle`), and the methods a document needs are shared by all three apps (`claudia_server.styles`, D203). Colour is a second axis beside the styles: `claudia_core.palette` holds the document's nine **colour roles**, a style writes `@accent` or `@accent/55`, and a client draws from the `resolved` form so that what reaches a browser stays literal (D200–D202). Every built-in style in all three apps is written in roles, so no literal colour is left anywhere in a new document. All three apps now have the style menu itself, not only the model behind it (D209): one `StyleMenu`/`StyleSpec`/`StylesDialog` reached through a `StyleHost`, with `objectStyleHost` making the selected floating object the thing a menu styles in creates and computes, `deviate_object_style` for "change this shape only", and a Format menu in each app in place of the inert "No styles yet" stub. Colour is picked by meaning: the picker lists roles by name and purpose, a literal colour reads as a deviation that one click adopts away, and the Colours dialog says what a change will cost before it is made, in plain words and never as a ratio (D210). **Not done:** `kind` on a style — composes' Format menu leaves the object styles out *by id* for want of it, which is the most visible place this now hurts; the full delete rules (`RemoveStyle` exists only as the undo of a create); upcasting of dropped properties; the style kinds for cells (E6.13); and a command that lets a person define a role of her own (`ReplacePalette` can bring a different set, which is what "the colours it started with" uses; nothing adds one).
