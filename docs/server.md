# The server (E3.1)

`python3 -m claudia_server` runs the process that holds documents. Everything a client does goes through one
WebSocket per person and document; the same protocol serves the Gtk client, the web app and the AI assistant.

```text
python3 -m claudia_server                          # https://127.0.0.1:8765, certificate made on first start
python3 -m claudia_server --web web/.output/public  # also serve the web app from the same address
python3 -m claudia_server --tls-cert c.pem --tls-key k.pem --tls-name claudia.example.org
python3 -m claudia_server --no-tls                  # plain text, for this computer only
python3 -m claudia_server --no-tls --host 0.0.0.0 --behind-proxy --allow-host claudia.example.org   # behind a TLS proxy
```

Documents are kept in memory until the container file exists (E2); they are gone when the server stops.

## Addresses

| Address | |
|---|---|
| `WebSocket /api/docs/{doc}/ws` | the live connection |
| `GET /api/health` | liveness |
| `GET /api/docs` | the documents on this server |
| `GET /api/protocol` | machine-readable description of every method, parameter and event |
| `GET /api/swagger` | the HTTP part, generated by FastAPI |

`GET /api/docs` answers `{app, documents}`. `app` is the kind of document this server hosts (`computes` or `creates`: a
server hosts one), so that a client knows what to create. `documents` lists the documents on the server: `id`, `app`,
`modified` and `online` (the number of people connected now), the most recently changed first. It shows that a document exists and nothing else: no user names, no content. Every
document has its own users and passwords, so opening one still needs its id, a name and a password. A server where even
the existence of a document should stay private starts with `--no-list` (the address then answers 404).

## Handshake

Credentials travel in the first frame, not in the URL (URLs end up in logs).

```json
{"id": 1, "method": "hello", "params": {"user": "ann", "password": "...", "create": false, "locale": "de"}}
```

The answer carries user, role, document, line, revision, people, limits and locale. With `"create": true` for a
document that does not exist, the document is made and the person becomes its owner. A wrong password, an unknown
name and a document that does not exist give the same answer. The name `ai` belongs to the assistant and cannot be
used.

`"locale"` is optional and always the client's own setting (E5.7, D31/D148 groundwork): there is no account profile
to keep it on. It is echoed back, normalized, in the welcome and on every connection the hub keeps — nothing reads it
yet, since no interface string has moved into a catalog. `PROTOCOL_VERSION` is **2** as of this field (was 1).

When the handshake fails the server answers and closes the socket with a code: 4400 bad request, 4401 unauthorized,
4403 foreign origin or host, 4404 no such document, 4408 no hello in time, 1013 too many connections, too many people
waiting to be let in, a full server or a client that is too slow.

On a server with an access secret, `"access": "<secret>"` goes into `hello` when a document is to be made, and
`Authorization: Bearer <secret>` into `GET /api/docs`; see *Who can reach the server* below.

## After the handshake

* Requests are `{"id", "method", "params"}`; responses `{"id", "ok", "result" | "error"}`; pushed events
  `{"event", "data"}`. The methods are the ones of `claudia_server.protocol.core_methods`; an app adds its own to a copy
  (`core_methods.extended()`).
* `apply` takes the command in its stored form and a `base` revision, the view the client was looking at. If the
  document has moved to another line since (a checkpoint was restored, or somebody took the way back) the edit is
  refused with `stale`, so nothing lands on a document the person is not looking at.
* Who receives what: command and state events go to everybody; `history` only to its author; a private chat message to
  its sender and recipient; ephemeral messages (presence, typing) are not echoed to the sender.
* The history panel reads `log` (the newest entries of the visible history, each with a sentence such as `B3 = 40`).
  Workbooks add `sheets`, `cells` (a window), `set_cells` (the text people typed; the server decides what it means),
  `add_sheet`, `structure`, `sizes` (a sheet's row heights and column widths away from the default) and
  `resize_lines` (D135: layout, not a cell style). Texts (`--model claudia_composes:TextModel`) add `blocks`, `suggestions`,
  `replace_text` (a range replaced by text; line breaks start paragraphs; one request is one history step),
  `set_style`, the style methods `styles`, `change_style`, `deviate_style`, `rename_style` and `check_css` (a style is
  CSS from the kernel's allow-list; a change either alters the style for all its uses or deviates into a new style
  that waits for its name), `look` and `hold` (where my cursor is, and locking the ± n words around it), `suggest` (assistant only)
  and `accept_suggestion` / `reject_suggestion`. The assistant has no direct write path into a text: it suggests,
  people accept (D63).
* **Help (E13).** `help_search` (an optional `query`, blank for everything) and `help_topic` (an id from a search result)
  read the help topics, which every app inherits for free the moment it has its own `help/` folder; nothing here needs a
  role, so the `ai` user can read it too. `help_search` only returns topics meant for the document's own app — a topic
  says which apps it is for in its own front matter, and a topic naming none is shown everywhere. `help_topic` is not
  re-scoped: an id already names one exact topic. Workbooks add `functions` (the same kind of search, over every cell
  function, library and core alike) and `function_help` (one function's signature, tooltip and full help text, by name).
* The AI is a participant called `ai`, one per document: it shows up in `users` and `people` (in the colour Iris), hears
  messages that start with `@ai`, and answers the asker only. It edits through the same methods as everybody, so locks
  and roles apply and its work is in the history under its name. The model behind it is a plug-in (`Engine`, or
  `AsyncEngine` for one that has to wait); the scripted stand-in understands a handful of phrases (`@ai help`) and
  `--no-assistant` switches it off.
* **A real model (`--ai`).** `python3 -m claudia_server --ai MODEL_DIR --ai-device GPU` makes the AI user answer with a
  language model that runs on the server's own machine with OpenVINO GenAI (`pip install claudia-server[openvino]`;
  a model converted with `optimum-cli export openvino --model Qwen/Qwen2.5-7B-Instruct --weight-format int4 qwen-ov`, or
  one of huggingface.co/OpenVINO). The device is `GPU` (default, decision D13), `CPU`, `NPU` or `AUTO`;
  `--ai-max-tokens` (512) limits an answer and `--ai-timeout` (180 s) the time it may take. The model is loaded before
  the server listens, so a wrong folder, a missing library or a device that is not there stops the server with a
  message that says what to do. Nothing leaves the machine. The questions of all documents wait in one queue and are
  answered one at a time, in order (`ModelRunner`); a document refuses more than four waiting questions. While the model
  works the event loop serves everybody else and the others see "ai is typing". A failure is answered in the chat
  ("I could not answer: ..."), never silently. In a workbook the model may ask for `set_cells`, `add_sheet`,
  `structure` and `resize_lines`; in a presentation (E7.9, D265) for `add_slide`, `add_object` (text boxes and
  shapes), `set_text`, `set_paragraph_style`, `move_object`, `resize_object` and `remove_object`, and it reads
  `slides`, `slide`, `shapes` and `styles` (`claudia_server.slide_lens`); it is told how in its prompt, built from
  the method table, and may ask for nothing else (`apps.MODEL_METHODS`). Each request that fails is reported to the
  asker with the reason. A presentation server without a model answers `@ai` that it has none. It remembers the last six exchanges with each person while the document is loaded.
  What is provisional: the prompt names the sheets but does not show cell contents yet (E7.5), and the answer is
  read as text with an optional fenced `commands` block (`claudia_ai.Agent`).
* Restoring a checkpoint and switching lines are **not on the wire yet**: the rules for who may do that in a live
  session are still to be decided.

## Safety

* TLS by default. The server's own certificate is self-signed; its fingerprint is printed at start-up. The desktop
  client trusts it like an SSH host (`claudia_client.TlsPolicy`): shown once, remembered, a changed certificate refused
  loudly. `--redirect-port` answers plain HTTP with a redirect to https and nothing else.
* Every HTTP answer says what a browser may do with the page (`claudia_server.security_headers`, SEC-13): a
  `Content-Security-Policy` with scripts from this server only (the start page's two inline scripts by their hash,
  read from the build at start), connections only to this server and its WebSocket, no plugins, and framing only by
  the server itself or a page on this computer (`http://127.0.0.1:*`, `http://localhost:*`: the Windows and macOS
  clients frame the web app in their local shell page, D251); plus `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: no-referrer` and a `Permissions-Policy` without camera, microphone and location. `/api/swagger`
  keeps only the framing rule while it loads from a CDN (SEC-14).
* A browser page cannot use a user's local server (see *Who can reach the server*).
* With `--dir DIR` every document is a sealed file (`docs/<id>.claudia` and a journal next to it): the content, the
  history, the chat and the names of the people are encrypted (AES-256-GCM), and the keys are opened by each person's
  password (Argon2id). Nothing readable is on disk, not even who the people are. A wrong password, an unknown name and a
  document that does not exist give the same answer in the same time. Passwords have at least 8 characters, a capital
  letter, a small letter and a digit. See `claudia-container` and the design in `e2-container-design.md`.
* The keys are held in memory only while a document is open, and are forgotten when the server unloads it. After a
  restart a **viewer** cannot bring a document up (a viewer holds only the content key): the first person to log in has
  to be an owner or editor; a viewer is told so (error `sealed`, close code 4423, and the web app keeps trying until
  somebody has opened it). Password hashing runs in threads, so it never stops the server; the hashes take turns
  (OpenSSL's Argon2id is not safe to run twice at once).
* **Packing.** Changes are appended to the journal as they happen. When a document is unloaded (and when the server is
  stopped, and every 500 changes while it is open) the journal is folded into the document file as sealed, chained
  blocks with a head record, and a snapshot is left, so that opening replays only what came after it. Somebody who
  holds the file but no key can still delete the newest blocks and the head together, or put back an older copy of the
  whole file; neither can be told from the file alone. Undo steps made before the snapshot are not restored when a
  document is opened.
* **Recovery key.** The owner of a new document is shown a recovery key (13 groups of 4 letters and digits) once, in the
  web app, before the document opens. It is the only way back in for somebody who forgot their password ("I forgot my
  password" on the start page: document, name, recovery key and a new password); that person keeps their role, and
  somebody who is not in the document becomes an owner. The server does not keep the key. An owner can make a new one
  in *Share* (the old one stops working). Whoever has the key can read the document: keep it away from the file.
* `--plain-dir DIR` is the old store of the early demos: plain files, scrypt hashes, **not encrypted**.
* Without a folder, passwords are stored in memory as scrypt hashes with a random salt.
* Limits: frame size, text length, regions per request, connections per document, documents per server, and the
  connections that may wait to be let in.

## Who can reach the server

Four rules, each of which can be loosened with one option and none of which needs a setting to be safe on a laptop.

**Names (SEC-01).** The server answers only to `localhost`, to IP addresses, to the name of the computer it runs on
and to the names it is told about with `--allow-host NAME` (repeatable; `--tls-name` and the name given with `--host`
count too). Any other `Host` gets 403, and a WebSocket is closed with 4403. This stops DNS rebinding: a web page can
point its own name (`evil.example`) at `127.0.0.1` and then talk to a server on its visitor's computer as if it were its
own origin, with a `Host` and an `Origin` that match. It cannot make a browser send a name the server knows as its own.
Behind a proxy that passes on the name people typed, add that name; the 403 page says so and the log names the refused
host once. IP addresses are always answered (a page has no name to rebind), except `0.0.0.0` and `::`. The `Origin` of a
WebSocket must also be the server itself or be named with `--allow-origin`; clients that are not browsers send none.

**Encryption (SEC-07).** Passwords travel in the first frame, and they also open the sealed documents, so plain text is
only for this computer: `--no-tls` on any other address is refused. A proxy that encrypts in front of the server is the
exception, and `--behind-proxy` says so (the start-up report keeps a warning). `scripts/start.py` needs `--tls` for a
`--host` other than this computer's.

**Limits (SEC-02).** `--max-documents N` (default 1000): past it nobody can make a document, and the refused one costs
no hashing and no disk. `--max-waiting N` (256) and `--max-waiting-per-address N` (64) bound the connections that have
connected but not yet logged in; the others are closed with 1013 at once, so a flood of `hello` frames cannot queue
behind the password hashing without end. Make the per-address limit larger where a whole school sits behind one address.

**Access secret (SEC-02, optional).** `--access-secret-file FILE`, or the environment variable `CLAUDIA_ACCESS_SECRET`
(a Docker secret or `-e`), at least 16 characters (`python3 -c "import secrets; print(secrets.token_urlsafe(24))"`).
Then only those who know it can make a document (`"access"` in `hello`) or read the list (`Authorization: Bearer ...`);
people who already have a document still log in with their name and password. Somebody without the secret who asks to
make a document is answered like somebody who asked for one that does not exist, so nothing is learned about which
documents there are. The secret is compared in constant time and never printed. The web app has no field for it yet.

Not there yet: redaction in packed blocks (E2.6: a redacted text still rests in older blocks), unencrypted export and import (E2.9), rate limits over time (E2.7: the caps above bound what is waiting, not how often an address may try), read restrictions for viewers and a viewer opening a sealed document first (E2.4).


## Presentations (creates)

A server started with `--model claudia_creates:SlideModel` hosts presentations. Its methods (see `GET /api/protocol`
for every parameter) are `slides`, `slide`, `shapes`, `images`, `styles`, `add_slide`, `add_object`, `add_image`,
`move_object`, `resize_object`, `set_text`, `set_snap` and `remove_object`, plus the core ones. A selection is the
region `{"kind": "objects", "slide": "s1", "ids": ["o1"]}` for `presence` and `lock`.

Each object also carries `snap` (E10.15): whether it holds to the grid, a helper the view draws on its own and
never sends to the server. `set_snap` takes an object's id and a `snap` boolean; releasing or re-snapping an
object is its own step in the document's history, independent of moving, resizing or editing it.

Positions and sizes are whole units of a slide of 1600 by 900. Shapes are JSON files, one per shape (the format is
described with `claudia_creates.shapes`); `--shapes DIR` adds a folder of them to the built-in rectangle, circle and
triangle. A document copies the outline of every shape it uses, so it opens the same on a server that does not have
the file. Each object refers to a named style (`styles`); the first draft has three, one of them (`plain-image`) for
pictures.

A picture is put on a slide with `add_image` (E10.8), not `add_object`: `data` is the file's bytes, base64, decoded
and validated server-side (at most 8 MB); `alt` is a required short description; `source_name` is the file's name
and `source_path` its full path, if the client could supply one — a plain web browser cannot, for its own security,
and sends `null`. The decoded picture is shared across every object that imports the same bytes, exactly like a
shape's outline, and listed by `images`. Clipboard and drag-and-drop import are not built yet; `add_image` only
takes a file chosen from disk. Everyone sees who imported a picture and when (`imported_by`, `imported_at`,
`source`, `source_name`), but `source_path` is sent only to the person who imported it — everyone else sees `null`
there, because a local disk path can expose more about someone's machine than the room should see.

The state events of a presentation arrive just before the `command` event of the change, like the cells of a table:
`objects` `{slide, changed: [object], removed: [id], order: [id]}` (`order` is the stacking order of the slide after the
change, the object in front last; `changed` is masked per connection as `slide` is, for the same reason), `shape`
`{id, definition | null}` (the document took in or let go of an outline) and `slides` `{}` (a slide was added or
removed: read `slides` again).
