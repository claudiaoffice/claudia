# The server (E3.1)

`python3 -m claudia_server` runs the process that holds documents. Everything a client does goes through one
WebSocket per person and document; the same protocol serves the Gtk client, the web app and the AI assistant.

```text
python3 -m claudia_server                          # https://127.0.0.1:8765, certificate made on first start
python3 -m claudia_server --web web/.output/public  # also serve the web app from the same address
python3 -m claudia_server --tls-cert c.pem --tls-key k.pem --tls-name claudia.example.org
python3 -m claudia_server --no-tls                  # behind a TLS-terminating proxy
```

Documents are kept in memory until the container file exists (E2); they are gone when the server stops.

## Addresses

| Address | |
|---|---|
| `WebSocket /api/docs/{doc}/ws` | the live connection |
| `GET /api/health` | liveness |
| `GET /api/docs` | the documents on this server |
| `GET /api/protocol` | machine-readable description of every method, parameter and event |
| `GET /api/swagger` | the HTTP part, generated by FastAPI |

`GET /api/docs` lists the documents on the server: `id`, `app`, `modified` and `online` (the number of people connected
now), the most recently changed first. It shows that a document exists and nothing else: no user names, no content. Every
document has its own users and passwords, so opening one still needs its id, a name and a password. A server where even
the existence of a document should stay private starts with `--no-list` (the address then answers 404).

## Handshake

Credentials travel in the first frame, not in the URL (URLs end up in logs).

```json
{"id": 1, "method": "hello", "params": {"user": "ann", "password": "...", "create": false}}
```

The answer carries user, role, document, line, revision, people and limits. With `"create": true` for a document that
does not exist, the document is made and the person becomes its owner. A wrong password, an unknown name and a document
that does not exist give the same answer. The name `ai` belongs to the assistant and cannot be used.

When the handshake fails the server answers and closes the socket with a code: 4400 bad request, 4401 unauthorized,
4403 foreign origin, 4404 no such document, 4408 no hello in time, 1013 too many connections or a client too slow.

## After the handshake

* Requests are `{"id", "method", "params"}`; responses `{"id", "ok", "result" | "error"}`; pushed events
  `{"event", "data"}`. The methods are the ones of `claudia_server.protocol.core_methods`; an app adds its own to a copy
  (`core_methods.extended()`).
* `apply` takes the command in its stored form and a `base` revision, the view the client was looking at. If the
  document has moved to another line since (a checkpoint was restored, or somebody took the way back) the edit is
  refused with `stale`, so nothing lands on a document the person is not looking at.
* Who receives what: command and state events go to everybody; `history` only to its author; a private chat message to
  its sender and recipient; ephemeral messages (presence, typing) are not echoed to the sender.
* The history panel reads `log` (the newest entries of the visible history, each with a sentence such as `B3 = 40`).
  Workbooks add `sheets`, `cells` (a window), `set_cells` (the text people typed; the server decides what it means),
  `add_sheet` and `structure`.
* The AI is a participant called `ai`, one per document: it shows up in `users` and `people` (in the colour Iris), hears
  messages that start with `@ai`, and answers the asker only. It edits through the same methods as everybody, so locks
  and roles apply and its work is in the history under its name. The model behind it is a plug-in (`Engine`); the
  scripted stand-in understands a handful of phrases (`@ai help`) and `--no-assistant` switches it off.
* Restoring a checkpoint and switching lines are **not on the wire yet**: the rules for who may do that in a live
  session are still to be decided.

## Safety

* TLS by default. The server's own certificate is self-signed; its fingerprint is printed at start-up. The desktop
  client trusts it like an SSH host (`claudia_client.TlsPolicy`): shown once, remembered, a changed certificate refused
  loudly. `--redirect-port` answers plain HTTP with a redirect to https and nothing else.
* A browser page from another origin cannot use a user's local server: the WebSocket refuses a foreign `Origin` unless
  it is named with `--allow-origin`.
* With `--dir DIR` every document is a sealed file (`docs/<id>.claudia` and a journal next to it): the content, the
  history, the chat and the names of the people are encrypted (AES-256-GCM), and the keys are opened by each person's
  password (Argon2id). Nothing readable is on disk, not even who the people are. A wrong password, an unknown name and a
  document that does not exist give the same answer in the same time. Passwords have at least 8 characters, a capital
  letter, a small letter and a digit. See `claudia-container` and the design in `e2-container-design.md`.
* The keys are held in memory only while a document is open, and are forgotten when the server unloads it. After a
  restart a **viewer** cannot bring a document up (a viewer holds only the content key): the first person to log in has
  to be an owner or editor; a viewer is told so. Password hashing runs in threads, at most two at a time, so it never
  stops the server.
* `--plain-dir DIR` is the old store of the early demos: plain files, scrypt hashes, **not encrypted**.
* Without a folder, passwords are stored in memory as scrypt hashes with a random salt.
* Limits: frame size, text length, regions per request, connections per document.

Not there yet: packing the journal into blocks and the head record (E2.1/E2.6), the recovery key in the server and web UI (E2.5), unencrypted export and import (E2.9), rate limiting (E2.7), read restrictions for viewers (E2.4).
