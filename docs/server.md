# The server (E3.1)

`python3 -m claudia_server` runs the process that holds documents. One server hosts all three apps — computes,
composes and creates — as modules (D430); `--apps` names fewer. Everything a client does goes through one WebSocket
per person and document; the same protocol serves the desktop clients, the web app and the AI assistant.

```text
python3 -m claudia_server                          # https://127.0.0.1:8765, all three apps, certificate made on first start
python3 -m claudia_server --web web/.output/public  # also serve the web app from the same address
python3 -m claudia_server --dir ~/claudia-docs     # keep documents, each app's in ~/claudia-docs/<app>/
python3 -m claudia_server --apps composes,creates  # only these apps
python3 -m claudia_server --model claudia_composes:TextModel --dir d   # one app, documents directly in d/ (D433)
python3 -m claudia_server --exit-when-idle 300     # stop once nothing has used the server for 5 minutes (D434)
python3 -m claudia_server --tls-cert c.pem --tls-key k.pem --tls-name claudia.example.org
python3 -m claudia_server --no-tls                  # plain text, for this computer only
python3 -m claudia_server --no-tls --host 0.0.0.0 --behind-proxy --allow-host claudia.example.org   # behind a TLS proxy
```

Without `--dir` documents are kept in memory and are gone when the server stops. A server takes a lock on its `--dir`
(D435): a second server on the same folder refuses to start.

## Addresses

| Address | |
|---|---|
| `WebSocket /api/{app}/docs/{doc}/ws` | the live connection to a document of `app` |
| `WebSocket /api/docs/{doc}/ws` | the live connection without the app (the address before D431) |
| `WebSocket /api/presence` | carries nothing; a page without a document keeps it open so the server knows it is in use |
| `GET /api/health` | liveness: `{ok, apps}`, and `version` to a request from this computer to `127.0.0.1`/`localhost` (D445) |
| `GET /api/docs` | the documents of every app on this server |
| `GET /api/{app}/docs` | the documents of one app |
| `POST /api/docs/lookup` | the document with exactly this uid, in any app (D535) |
| `GET /api/{app}/protocol` | machine-readable description of every method, parameter and event of `app` |
| `GET /api/protocol` | the same for the first app |
| `GET /api/swagger` | the HTTP part, generated by FastAPI |

`GET /api/docs` answers `{app, apps, documents}`. `apps` are the apps this server hosts, in order; `app` is the one
app of a server that hosts one, else `null`. `documents` lists the documents on the server: `id`, `app`, `modified`
`online` (the number of people connected now), `description` (Markdown) and `tags` (a list of words), the most recently
changed first. `description` and `tags` are what an editor or owner of the document said about it: they are plain in the file's
manifest, so anybody who may list the server may read and search them, without a password (D530). `GET /api/{app}/docs` answers
`{app, documents}` for one app. A list shows that a document exists and what its owner chose to say about it: no user names, no content.
Every document has its own users and passwords, so opening one still needs its id, a name and a password. A server
where even the existence of a document should stay private starts with `--no-list` (the addresses then answer 404).

Ids are unique per app, not per server (D431): `notes` can be a workbook and a text at once, and the address with the
app is never ambiguous. The address without it opens the document of the first app (in the order of `--apps`) that has
one, and makes a new document in the app `hello.app` names, else in the first app.

## Handshake

Credentials travel in the first frame, not in the URL (URLs end up in logs).

```json
{"id": 1, "method": "hello", "params": {"user": "ann", "password": "...", "create": false, "locale": "de"}}
```

The answer carries user, role, document, line, revision, people, limits and locale. With `"create": true` for a
document that does not exist, the document is made and the person becomes its owner. What a new document starts with (a
workbook's first sheet, a text's or presentation's language, from `locale` below) the server makes then, as one
`core.Setup` entry by its maker that is nobody's undo step (UX-33, D362). A wrong password, an unknown
name and a document that does not exist give the same answer. The name `ai` belongs to the assistant and cannot be
used.

`"locale"` is optional and always the client's own setting (E5.7, D31/D148 groundwork): there is no account profile
to keep it on. It is echoed back, normalized, in the welcome and on every connection the hub keeps, and the server
says its own messages in it (D322): the `message` of an error, of a refused `hello` and of a `HubError` comes in the
language of the connection when there is a catalog for it (German now), else in English. `code` and `detail` never
change with the language, so a client branches on those. What the document packages raise is English for now (E5.17).
`PROTOCOL_VERSION` is **2** as of this field (was 1).

When the handshake fails the server answers and closes the socket with a code: 4400 bad request, 4401 unauthorized,
4403 foreign origin or host, 4404 no such document, 4408 no hello in time, 4429 too many tries, 1013 too many connections,
too many people waiting to be let in, a full server or a client that is too slow.

**Wrong passwords make the next try wait** (D1266, `login_throttle.py`). Three tries are free; after that each wrong
password makes the next try wait 1, 2, 4, 8 … seconds, at most 30 per address and 10 per document and name, and the wait is
forgotten after 15 quiet minutes. A `hello` inside a wait is refused **before any hashing** with the error `too_many_tries`,
close code 4429 and `retry_after` (whole seconds); the administrator's sign-in answers `429` with a `Retry-After` header
and `retry_after` in its JSON. The right password does not get around a wait, nobody is locked out for good, and the state
is in memory: a restart forgets it (D1276). Behind a proxy the address is counted as `--proxy-hops` says (D1275).

On a server with an access secret, `"access": "<secret>"` goes into `hello` when a document is to be made, and
`Authorization: Bearer <secret>` into `GET /api/docs`; see *Who can reach the server* below.

## The uid of a document

Every document has a random `uid` (a UUID v4) in the plain manifest of its file (D533). It is not in any list and no
screen shows it; the welcome of a connection carries it as `uid` (`null` for a store that has none). `POST
/api/docs/lookup` with the body `{"uid": "<uuid>"}` answers `{app, id, modified}` for the document of any app of the
server that has exactly this uid, and 404 `no such document here` for any other value, whether it is no uid or an
unknown one; 400 if the body is not `{"uid": ...}`. It answers whoever may read the list: nothing on a server started
with `--no-list`, `Authorization: Bearer <secret>` on one with an access secret. One address may ask 60 times a
minute (429). A file that is placed keeps its uid; a server never holds two documents with one uid (D535).

## Opening a file from the computer

A Word, Excel, PowerPoint or OpenDocument file becomes a new document in two steps (D440):

1. `POST /api/uploads` with the file as the body and its name in `X-Claudia-Name` (percent-encoded). The server looks
   at the bytes, holds them for five minutes and answers what the file is:
   `{upload, name, format, app, size, hosted, suggested_id, kind, description, tags}`; the last two are what the file
   says about itself (Dublin Core description and keywords of an Office or OpenDocument file), to offer as a start
   (D531). Formats: docx and odt (composes), xlsx and ods
   (computes), pptx and odp (creates). At most 64 MB; 16 uploads wait at once, 4 from one address; with an access
   secret only `Authorization: Bearer <secret>` may upload. 415 for anything else, 413 for too large.
2. `hello` at `/api/<app>/docs/<id>/ws` with `"create": true, "upload": "<token>"` and the new owner's name and
   password. The document starts with one `core.Import` entry holding what the file shows (D438); the file itself is
   kept, sealed, in the document unless `"keep_original": false` (D439). `"description"` (text) and `"tags"` (a list of
   words) are optional and go into the plain manifest (D530, D531); a value that does not fit is refused as
   `bad_request` before anything is made. The welcome says `imported: {name, format, kept, losses, described}`.

`export_office` in the same format then gives back the kept file with only the edits patched in (`patched: true`);
everything Claudia does not show stays as it was (D441). Other formats are written anew.

A Claudia file is uploaded the same way; the answer has its `id` (its name), its own `description` and `tags`, whether
this server already holds a document of that name (`exists`), and `same_document`: the name of the document here that
is the very same one (the file's uid is here already), else `null`. `POST /api/uploads/<token>/place` puts it into its
app's folder as it is, uid included, and the person opens it with a name and password it knows (D442). It never
overwrites (409), refuses a document that is here already, under whatever name and in whatever app (409, with a
sentence naming the one that is here, D535), and a server that keeps documents in memory cannot take one in (422).

An **unencrypted Claudia export** (`.claudia-export.zip`, D1270, D1272; the layout is in [the format](container-format.md))
is uploaded the same way. The answer has `format: "claudia-export"`, `kind: "Claudia export"`, `app`, `made_by` and
`made_at` (who exported it and when, as the file says: the dialog shows it, nothing trusts it) and a `suggested_id` made
from the file's name; `hosted` says whether this server has the app. The second step is the one of an Office file with
`"create": true, "upload": "<token>"`: the document starts with one `core.Import` entry, the importer is its only owner,
and the file is **not** kept inside (`keep_original` is ignored). The state must be of the shape the app of this server
uses (`state_schema`); another version is refused with a sentence. Nobody named in the export is given access.

## What leaves the document is recorded (D1271)

`export_content`, `export_office` and `export_claudia` are marked `leaves="export"` in the method table: after the method
has answered, `MethodTable.dispatch` records who (the account of the connection), when, the format and the parts in the
document's audit chain (`AuditDirectory.record_audit`; the document holds the keys of everybody who opened it, so a
viewer's export is recorded too). A print or a PDF is made in the browser, so the window reports it: `report_output
{kind: "print"|"pdf", format, pages}`; the server takes the name from the connection and ignores any name a client could
send, limits one person to 20 reports a minute (`too_many`) and refuses a page count that is not a number between 0 and
100 000. `audit_log` reads the record (history: owners and editors; a viewer gets `forbidden`). The other windows of
owners and editors are told with the ephemeral event `audit_recorded`; the window that asked is not, and reads the record
again. `export_claudia {include_history}` is the unencrypted zip as base64 (`format: "claudia-unencrypted"`); the history
and chat go in only for an owner (`forbidden` otherwise).

## Roles change and people are removed (D1263, D1284)

`change_role {name, role}` (`role` is `editor` or `viewer`) and `remove_person {name}` are for owners (`forbidden`
otherwise); an owner cannot be lowered or removed (`command_error`: ownership is handed over, `propose_owner`). Both answer
after the keys the person held are renewed (`SealedDocuments`; the answer of `change_role` is `{user, role, renewed}`). The
renewal runs under the document's lock on the event loop (D1282): for a normal document it takes about as long as writing
the file once, and a long one stops the server's other documents for that time. The person's open windows follow at once:
the ephemeral events `role_changed {user, role}` and `person_removed {user}` go to everybody in the document, the new role
applies to her connections before the event is delivered, and after `person_removed` her connections get nothing more and
answer `forbidden`. A person who was away gets the new keys at her next login, from her inbox in the file (D1274).

## After the handshake

* Requests are `{"id", "method", "params"}`; responses `{"id", "ok", "result" | "error"}`; pushed events
  `{"event", "data"}`. The methods are the ones of `claudia_server.protocol.core_methods`; an app adds its own to a copy
  (`core_methods.extended()`).
* `apply` takes the command in its stored form and a `base` revision, the view the client was looking at. If the
  document has moved to another line since (a checkpoint was restored, or somebody took the way back) the edit is
  refused with `stale`, so nothing lands on a document the person is not looking at.
* Who receives what: command and state events go to everybody; `history` only to its author; a private chat message to
  its sender and recipient; ephemeral messages (presence, typing) are not echoed to the sender.
* The history panel reads `log` (the newest entries of the visible history, each with a sentence such as `B3 = 40`).
  Workbooks add `sheets`, `cells` (a window), `set_cells` (the text people typed; the server decides what it means),
  `add_sheet`, `structure`, `sizes` (a sheet's row heights and column widths away from the default) and
  `resize_lines` (D135: layout, not a cell style), and search and replace (E6.20): `search_find` (what a search
  finds in text, formulas and values, with where, how it reads, what a replacement would make of it and the cells it
  left out with the reason), `search_preview` (what `search_replace` would change, and what it skips because somebody
  holds it) and `search_replace` (one history step; cells held by somebody else are skipped and named, not refused). A
  query is one of `{mode: "text"}`, `{mode: "builder"}` or `{mode: "pattern"}` (`claudia_search`); a mistake in a
  pattern comes back as `error: {message, field, position}` so that a client can show it while a person types. Every
  place in an answer is `at`, the app's own description of it (a cell: `{sheet, row, col}`), and `leave` sends the
  same `at` back (`{at, match}`). One request searches for two seconds at most, inside a pattern too (`regex` with a
  timeout, SEC-18): `timed_out` says it stopped, and `search_replace` then refuses rather than replace part of it. Texts (`--model claudia_composes:TextModel`) add `blocks`, `suggestions`,
  `replace_text` (a range replaced by text; line breaks start paragraphs; one request is one history step),
  `set_style`, the style methods `styles`, `change_style`, `deviate_style`, `rename_style`, `set_heading_level` and
  `check_css` (a style is CSS from the kernel's allow-list; a change either alters the style for all its uses or deviates
  into a new style that waits for its name; a paragraph style may give a heading level, E9.22), `style_deletion`, `delete_style` and `hide_style` (D226, D785: a deletion is one undo step; `how` is `assign` (another style takes its place, looks change) or `rebase` (looks held, with a stand-in that waits for its name); built-in and template styles can only be hidden), `look` and `hold` (where my cursor is, and locking the ± n words around it), `suggest` (assistant only)
  and `accept_suggestion` / `reject_suggestion`. The assistant writes a text as it writes a sheet or a slide (D640):
  for a person in *act* mode through `replace_text` and `set_style`, in *suggest* mode through `suggest`, and people
  accept (D262).
* **Objects (D177, CODE-27).** The three apps answer the same methods for the objects on a sheet, a slide or in a
  text: `images`, `add_image`, `describe_object`, `move_object`, `resize_object`, `rotate_object`, `remove_object`,
  and the containers' `add_container`. Only the words that say where differ: a cell (`sheet`, `row`, `col`),
  a point on a slide (`slide`, `x`, `y`), a character of a text (`block`, `offset`, and for a move `dx`, `dy`). A text also answers `shapes` and `add_object` (a text box or a shape, `add_object` with `kind`, `w`, `h`, optional `shape` and `text`; D1065) and `set_wrap` (`id`, `wrap` one of `over`, `around`, `above-below`, `behind`, optional `gap` in pixels; D1061). `add_object` and `move_object` in a text may carry `wrap` and `gap`. **Breaking, 0.x:** `shapes` of a text answers `{library, document}`, not a list.
* **Help (E13).** `help_search` (an optional `query`, blank for everything) and `help_topic` (an id from a search result)
  read the help topics, which every app inherits for free the moment it has its own `help/` folder; nothing here needs a
  role, so the `ai` user can read it too. `help_search` only returns topics meant for the document's own app — a topic
  says which apps it is for in its own front matter, and a topic naming none is shown everywhere. `help_topic` is not
  re-scoped: an id already names one exact topic. Workbooks add `functions` (the same kind of search, over every cell
  function, library and core alike) and `function_help` (one function's signature, tooltip and full help text, by name).
* The AI is a participant called `ai`, one per document: it shows up in `users` and `people` (in the colour Iris), hears
  messages that start with `@ai`, and answers the asker only. It edits through the same methods as everybody, so locks
  and roles apply and its work is in the history under its name. The model behind it is a plug-in (`Engine`, or
  `AsyncEngine` for one that has to wait); the scripted stand-in understands a handful of phrases (`@ai help`) and
  `--no-assistant` switches it off.
* **A real model (`--ai`).** `python3 -m claudia_server --ai MODEL_DIR --ai-device GPU` makes the AI user answer with a
  language model that runs on the server's own machine with OpenVINO GenAI (`pip install claudia-server[openvino]`;
  a model converted with `optimum-cli export openvino --model Qwen/Qwen2.5-7B-Instruct --weight-format int4 qwen-ov`, or
  one of huggingface.co/OpenVINO). The device is `GPU` (default, decision D13), `CPU`, `NPU` or `AUTO`;
  `--ai-max-tokens` (512) limits an answer and `--ai-timeout` (180 s) the time it may take. The model is loaded before
  the server listens, so a wrong folder, a missing library or a device that is not there stops the server with a
  message that says what to do. Nothing leaves the machine. The questions of all documents wait in one queue and are
  answered one at a time, in order (`ModelRunner`); a document refuses more than four waiting questions. While the model
  works the event loop serves everybody else and the others see "ai is typing". A failure is answered in the chat
  ("I could not answer: ..."), never silently. In a workbook the model may ask for `set_cells`, `add_sheet`,
  `structure`, `resize_lines` and `search_replace`; in a presentation (E7.9, D265) for `add_slide`, `add_object` (text boxes and
  shapes), `set_text`, `set_paragraph_style`, `move_object`, `resize_object` and `remove_object`, and it reads
  `slides`, `slide`, `shapes` and `styles` (`claudia_server.slide_lens`); in a text (E7.10, D680) for `replace_words`,
  `add_paragraphs` and `set_style` when the asker chose *act* and `suggest_words` when she chose *suggest*, naming
  paragraphs by id and words by quoting them (D681), and it reads `paragraphs`, `outline`, `styles` and `suggestions`
  (`claudia_server.document_lens`); it is told how in its prompt, built from
  the method table, and may ask for nothing else (`apps.MODEL_METHODS`). Each request that fails is reported to the
  asker with the reason. A presentation server without a model answers `@ai` that it has none. It remembers the last six exchanges with each person while the document is loaded.
  What is provisional: the prompt names the sheets but does not show cell contents yet (E7.5), and the answer is
  read as text with an optional fenced `commands` block (`claudia_ai.Agent`).
* Restoring a checkpoint and switching lines are **not on the wire yet**: the rules for who may do that in a live
  session are still to be decided.

## Safety

* TLS by default. The server's own certificate is self-signed; its fingerprint is printed at start-up. The Linux
  client trusts it like an SSH host (`claudia_shell_gtk.trust`, its "Trust this server?" dialog): shown once,
  remembered, a changed certificate asked about again. The macOS and Windows clients do not ask yet and refuse it. `--redirect-port` answers plain HTTP with a redirect to https and nothing else.
* Every HTTP answer says what a browser may do with the page (`claudia_server.security_headers`, SEC-13): a
  `Content-Security-Policy` with scripts from this server only (the start page's two inline scripts by their hash,
  read from the build at start), connections only to this server and its WebSocket, no plugins, and framing only by
  the server itself or a page on this computer (`http://127.0.0.1:*`, `http://localhost:*`: the Windows and macOS
  clients frame the web app in their local shell page, D251); plus `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: no-referrer` and a `Permissions-Policy` without camera, microphone and location. `/api/swagger`
  keeps only the framing rule while it loads from a CDN (SEC-14).
* A browser page cannot use a user's local server (see *Who can reach the server*).
* With `--dir DIR` every document is a sealed file (`docs/<id>.claudia` and a journal next to it): the content, the
  history, the chat and the names of the people are encrypted (AES-256-GCM), and the keys are opened by each person's
  password (Argon2id). Nothing readable is on disk, not even who the people are. A wrong password, an unknown name and a
  document that does not exist give the same answer in the same time. Passwords have at least 8 characters, a capital
  letter, a small letter and a digit. See `claudia-container` and the design in `e2-container-design.md`.
* The keys are held in memory only while a document is open, and are forgotten when the server unloads it. After a
  restart a **viewer** cannot bring a document up (a viewer holds only the content key): the first person to log in has
  to be an owner or editor; a viewer is told so (error `sealed`, close code 4423, and the web app keeps trying until
  somebody has opened it). Password hashing runs in threads, so it never stops the server, **also for requests that confirm a
  password** (`set_details`, `download_claudia`, `change_password`, `add_user` and the others that say `hashes` in
  `describe`): the gateway hashes them in a worker thread, at most two at once, before it handles them (SEC-21). The result
  is held for at most 30 s and used once. The hashes take turns (OpenSSL's Argon2id is not safe to run twice at once).
* **What a viewer is shown** (D1261). A viewer holds only the content key, and the server sends her only what it opens:
  the content, the names of the people and presence. Nothing of the history, the chat, a checkpoint, a redaction or a
  restore is pushed to her, a `command` event is reduced to its type and revision, and `welcome` has no history parts.
  Every method says what it reads (`reads` in `describe`: `content`, `history` or `chat`), and a viewer who calls one that
  reads the history or the chat gets `forbidden`. A new event or method is for owners and editors until it is classified
  (`audience.py`). *Who wrote which stretch* is part of the content and is still shown (bug SEC-22).
* **The cost of hashing** for new documents is measured when the server starts (about 0.75 s, up to 256 MiB), in the
  background; until then, and on a machine too slow for it, the minimum applies (3 passes over 64 MiB). Server settings ▸
  Security sets the target time. A document keeps the cost it was made with.
* **Packing.** Changes are appended to the journal as they happen. When a document is unloaded (and when the server is
  stopped, and every 500 changes while it is open) the journal is folded into the document file as sealed, chained
  blocks with a head record, and a snapshot is left, so that opening replays only what came after it. Somebody who
  holds the file but no key can still delete the newest blocks and the head together, or put back an older copy of the
  whole file; neither can be told from the file alone. Undo steps made before the snapshot are not restored when a
  document is opened.
* **Recovery key.** The owner of a new document is shown a recovery key (13 groups of 4 letters and digits) once, in the
  web app, before the document opens. It is the only way back in for somebody who forgot their password ("I forgot my
  password" on the start page: document, name, recovery key and a new password); that person keeps their role, and
  somebody who is not in the document becomes an owner. The server does not keep the key. An owner can make a new one
  in *Share* (the old one stops working). Whoever has the key can read the document: keep it away from the file.
* `--plain-dir DIR` is the old store of the early demos: plain files, scrypt hashes, **not encrypted**.
* Without a folder, passwords are stored in memory as scrypt hashes with a random salt.
* Limits: frame size, text length, regions per request, connections per document, documents per server, and the
  connections that may wait to be let in.

## Who can reach the server

Four rules, each of which can be loosened with one option and none of which needs a setting to be safe on a laptop.

**Names (SEC-01).** The server answers only to `localhost`, to IP addresses, to the name of the computer it runs on
and to the names it is told about with `--allow-host NAME` (repeatable; `--tls-name` and the name given with `--host`
count too). Any other `Host` gets 403, and a WebSocket is closed with 4403. This stops DNS rebinding: a web page can
point its own name (`evil.example`) at `127.0.0.1` and then talk to a server on its visitor's computer as if it were its
own origin, with a `Host` and an `Origin` that match. It cannot make a browser send a name the server knows as its own.
Behind a proxy that passes on the name people typed, add that name; the 403 page says so and the log names the refused
host once. IP addresses are always answered (a page has no name to rebind), except `0.0.0.0` and `::`. The `Origin` of a
WebSocket must also be the server itself or be named with `--allow-origin`; clients that are not browsers send none.

**Encryption (SEC-07).** Passwords travel in the first frame, and they also open the sealed documents, so plain text is
only for this computer: `--no-tls` on any other address is refused. A proxy that encrypts in front of the server is the
exception, and `--behind-proxy` says so (the start-up report keeps a warning). Behind a proxy, a person is counted by the `X-Forwarded-For` entry that the nearest trusted proxy appended, not by the proxy's own address, so per-address caps and waits do not hit everybody: `--proxy-hops N` says how many proxies set the header (default 1; 0 counts by the socket and ignores the header; the start-up report says which, D1275). `scripts/start.py` needs `--tls` for a
`--host` other than this computer's.

**Limits (SEC-02).** `--max-documents N` (default 1000), all apps together (D432): past it nobody can make a document,
and the refused one costs no hashing and no disk. `--max-waiting N` (256) and `--max-waiting-per-address N` (64) bound the connections that have
connected but not yet logged in; the others are closed with 1013 at once, so a flood of `hello` frames cannot queue
behind the password hashing without end. Make the per-address limit larger where a whole school sits behind one address.

**Access secret (SEC-02, optional).** `--access-secret-file FILE`, or the environment variable `CLAUDIA_ACCESS_SECRET`
(a Docker secret or `-e`), at least 16 characters (`python3 -c "import secrets; print(secrets.token_urlsafe(24))"`).
Then only those who know it can make a document (`"access"` in `hello`) or read the list (`Authorization: Bearer ...`);
people who already have a document still log in with their name and password. Somebody without the secret who asks to
make a document is answered like somebody who asked for one that does not exist, so nothing is learned about which
documents there are. The secret is compared in constant time and never printed. The web app has no field for it yet.

Redaction rewrites the document file and its journal (D725; `redaction_plan` and `redact`, owners on anything and editors on their own work, D727). Not there yet: unencrypted export and import (E2.9), the sealed inbox that gives everybody renewed keys after a role change or key renewal (E2.3, slice C).


## The first administrator (SEC-12)

The server settings (`/admin`, `/api/admin/*`) are for the server's administrators, a different identity from any
document's people. An administrator can make the server run programs (the LaTeX programs, SEC-16), so naming the first
one is kept to whoever runs the server, on every server, this computer's included (D1370):

* **The setup code.** At every start that ends with no administrator, the server makes a code of 12 characters
  (`K7QM-4TXR-92HB`; case, dashes and spaces do not matter, D1371) and says it only where its operator looks: in the
  start-up report, with a link to the settings pages that carries it in the fragment (`/admin#setup=...`, never sent
  to a server or a proxy, D1372), and in `admin/setup-code` of the state folder (`--state-dir`), readable by the
  server's account only. `POST /api/admin/setup` takes it as `code`; `POST /api/admin/setup-code` checks one without
  naming anybody. A wrong code is 403, a code from too many tries 429 with `Retry-After` (the sign-in's waits, D1266),
  and a code that comes after somebody was named 409. `GET /api/admin/status` says `"setup_code": true` while one is
  asked for; no answer contains the code. It dies when the first administrator is named or the server stops.
* **The desktop apps** read the code of their own server and hand it to their own page (`welcome.setup_code` of the
  shell contract, D1373): there nobody types it.
* **At start, for deployments:** `--admin NAME` (or `CLAUDIA_ADMIN`) with `--admin-password-file FILE` (or
  `CLAUDIA_ADMIN_PASSWORD_FILE`; the password is the file's first line) names NAME if there is nobody yet and never
  changes an administrator who exists (D1376). The container also takes `CLAUDIA_ADMIN_PASSWORD` as a variable and
  turns it into a private file.
* **Locked out:** `--reset-administrators` forgets every administrator at start (`admins.json` is kept aside as
  `admins-before-reset-<time>.json`); settings, fonts and documents stay (D1375). The next administrators see a note
  with the date and the names until one of them dismisses it (`GET` and `DELETE /api/admin/reset-note`).

A server behind a proxy counts as reachable from other computers whatever its `--host` (D1374).

## Presentations (creates)

The creates module hosts presentations. Its methods (see `GET /api/protocol`
for every parameter) are `slides`, `slide`, `shapes`, `images`, `styles`, `add_slide`, `add_object`, `add_image`,
`move_object`, `resize_object`, `set_text`, `set_snap` and `remove_object`, plus the core ones. A selection is the
region `{"kind": "objects", "slide": "s1", "ids": ["o1"]}` for `presence` and `lock`.

Each object also carries `snap` (E10.15): whether it holds to the grid, a helper the view draws on its own and
never sends to the server. `set_snap` takes an object's id and a `snap` boolean; releasing or re-snapping an
object is its own step in the document's history, independent of moving, resizing or editing it.

Positions and sizes are whole units of a slide of 1600 by 900. Shapes are JSON files, one per shape (the format is
described with `claudia_creates.shapes`); `--shapes DIR` adds a folder of them to the built-in rectangle, circle and
triangle. A document copies the outline of every shape it uses, so it opens the same on a server that does not have
the file. Each object refers to a named style (`styles`); the first draft has three, one of them (`plain-image`) for
pictures.

A picture is put on a slide with `add_image` (E10.8), not `add_object`: `data` is the file's bytes, base64, decoded
and validated server-side (at most 8 MB); `alt` is a required short description; `source_name` is the file's name
and `source_path` its full path, if the client could supply one — a plain web browser cannot, for its own security,
and sends `null`. The decoded picture is shared across every object that imports the same bytes, exactly like a
shape's outline, and listed by `images`. Clipboard and drag-and-drop import are not built yet; `add_image` only
takes a file chosen from disk. Everyone sees who imported a picture and when (`imported_by`, `imported_at`,
`source`, `source_name`), but `source_path` is sent only to the person who imported it — everyone else sees `null`
there, because a local disk path can expose more about someone's machine than the room should see.

The state events of a presentation arrive just before the `command` event of the change, like the cells of a table:
`objects` `{slide, changed: [object], removed: [id], order: [id]}` (`order` is the stacking order of the slide after the
change, the object in front last; `changed` is masked per connection as `slide` is, for the same reason), `shape`
`{id, definition | null}` (the document took in or let go of an outline) and `slides` `{}` (a slide was added or
removed: read `slides` again).
